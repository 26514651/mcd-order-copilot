# 服务边界与合规红线

> 这份文件回答一个问题：**这个工具能对谁说、不能对谁说、说的分寸在哪里。**
>
> 它是 `skill/mcd-order-copilot/SKILL.md` 三条原则的展开版。写代码时遇到"这个功能要不要做"，
> 来这里找答案，不要临场发挥。

---

## 1. 为什么需要这份文件

麦当劳的菜品数据涉及**营养**和**健康**，这两个词距离"医疗建议"只有一步之遥。

本项目的数据源是麦当劳 MCP 官方接口，它提供的是**营养素数值**（能量、蛋白、脂肪、碳水、钠、钙），
**不提供**任何临床判断所需的字段：没有 GI、没有过敏原、没有配料级明细、没有食用建议。

所以边界不是"我们想不想做"，而是**数据支不支持**。下面每一条红线都标注了它卡在哪个字段上。

---

## 2. 人群三级边界

| 级别 | 人群 | 处理方式 | 依据 |
|---|---|---|---|
| 🟢 **绿灯** | 增肌 / 减脂 / 增肌减脂 / 高蛋白 / 控热量 / 控脂 / 控钠 / 控碳水 / 训练前后补给 | 正常筛选与排序，可给参考区间 | 这些目标只需要"数值 + 允许上下限"，官方字段足够 |
| 🟡 **黄灯** | 控糖（血糖管理） | **只呈现碳水总量数字**，禁用「推荐」「适合」「可以吃」等判断词 | 官方**无 GI 值**。同样 40g 碳水，来自可乐和来自全麦面包对血糖的影响完全不同，只看总量无法区分 |
| 🔴 **红灯** | 糖尿病 / 肾病 / 孕期 / 儿童 / 进食障碍 / **食物过敏** | **不做任何推荐**，只提示咨询医生或门店 | 官方**无过敏原字段**、无临床指标。做推荐等于编造 |

### 红灯为什么是绝对红线

食物过敏是**可能致死**的场景。官方接口里没有过敏原数据，任何"这个你可以吃"的输出
都是基于不完整信息的猜测。**宁可什么都不说。**

同理，肾病需要控钾控磷 —— 官方字段里没有钾和磷，只有钠和钙。缺失即不可服务。

## 3. 数据层面的红线（不可做清单）

| 编号 | 不做的事 | 原因 | 替代做法 |
|---|---|---|---|
| D1 | **不估算缺失营养值** | 用同类产品推算会造出一个看似权威的假数字 | 显示「官方暂无数据」，并说明该项不参与筛选 |
| D2 | **不把缺失当 0** | 缺失填 0 会让总热量凭空变低，方向性错误 | 缺失即排除该餐品出筛选结果，不参与加总 |
| D3 | **不做无官方依据的差值** | 接口只返回"可去掉哪些配料"，不返回"去掉后营养变化" | 只列可去掉的配料清单，**不说**"去酱省 90 kcal" |
| D4 | **不给套餐做名称匹配** | `巨无霸三件套` 含巨无霸，但它的热量不是巨无霸的热量 | 走 `rounds` 成分加总；结构不可解就如实报告不可用 |
| D5 | **不假设营养单位口径** | 官方未标注"每份"还是"每 100g" | 界面统一按「每份」展示并显式注明这是本项目的口径 |
| D6 | **不用第三方数据补位** | 第三方热量表同一款汉堡能查出 503 / 530 / 602 三个值 | 只用官方接口；官方没有就承认没有 |

> D3 和 D4 是最容易被"做得更完整"的冲动攻破的两条。它们是这个项目区别于
> 一张静态热量表的核心 —— **能算的算准，不能算的说清楚**。

## 4. 表达层面的红线

### 4.1 语气规范

| 不要 | 要 |
|---|---|
| 「这个很健康」「这个不健康」 | 「这一份的钠是 961 mg」 |
| 「减脂期千万别吃这个」 | 「这一份的热量是 513 kcal，超出你设的 600 kcal 上限的 86%」 |
| 「麦辣鸡腿汉堡是垃圾食品」 | （不评价品牌与产品，只呈现数字） |
| 「建议你吃巨无霸」 | 「按你设的条件（蛋白 ≥ 30g），符合的有 4 项」 |
| 「你吃太多了」 | （不做道德判断，数字自己说话） |

**核心原则：数据说人话，判断不说假话。**

不制造食物罪恶感。用户来查数字是为了做决定，不是为了被评判。

### 4.2 禁止事项

| 禁止 | 说明 |
|---|---|
| **品牌对比** | 不做"比 XX 家更健康"这类横向对比 |
| **贬低品牌** | 不评价麦当劳的产品本身 |
| **暗示官方背书** | 不得表述为"麦当劳官方推荐""官方合作" |
| **使用官方商标与专有字体** | 配色可用通用色（金/红），但**不得**使用麦当劳 Logo、M 形标志、官方专有字体 |
| **医疗建议** | 不诊断、不建议、不承诺疗效 |

## 5. 标准免责声明

任何面向用户的输出（CLI、演示页、Skill 回复）**结尾必须带**：

> 数据来自麦当劳 MCP 官方接口 · 本项目非麦当劳官方产品 · 营养信息仅供参考，不构成医疗、营养或任何专业建议。

演示页底部、README 末尾、每条 CLI 输出都要有。这不是形式主义 ——
它是"我们知道自己边界在哪"的对外声明。

---

## 6. 预设值的来源规范

`src/mcd_order_copilot/profiles.py` 里的目标区间必须遵守：

1. **用整数下限/上限**，不用伪精度。写「蛋白 ≥ 30 g」，不写「蛋白 32.7 g」——
   后者暗示了一个本项目并不具备的临床依据。
2. **每个预设必须有一句人话解释**。解释不了为什么给这个数，就不该给。
3. **标为参考值**。输出中明确「非医疗或营养处方」。
4. **体重折算可选**，且按通用 per-kg 系数折算后必须标注「按体重估算」。

## 7. 参赛合规

| 项 | 要求 |
|---|---|
| `CONTEST_DECLARATION.md` | 内容与官方版本**逐字节一致**，一个字都不能改 |
| MCP Token | **不得**出现在仓库任何文件中。只走环境变量 `MCD_MCP_TOKEN`，示例文件只用 `${MCD_MCP_TOKEN}` 占位 |
| 写操作工具 | 本项目**不调用**下单、取消、积分兑换、抽奖等任何写操作 |
| 数据来源声明 | 所有营养、价格、图片均标注来自麦当劳 MCP 官方接口 |

---

## 8. 若要扩展到医疗方向，前置条件

如果未来真的要服务糖尿病、肾病或过敏人群，**必须先补齐**：

| 缺口 | 需要的字段 | 当前状态 |
|---|---|---|
| 升糖管理 | GI / GL 值 | ❌ 官方无 |
| 肾病 | 钾、磷 | ❌ 官方无 |
| 过敏人群 | 过敏原清单 | ❌ 官方无（且属安全红线，非"暂时没有"） |
| 配料级控制 | 各配料单独营养 | ❌ 官方只返回可去掉的配料名，不返回其营养 |
| 单位口径 | 每份 / 每 100g 标注 | ⚠️ 官方未标注，本项目统一按每份 |

**在这些字段到位之前，相关人群一律走红灯处理。**
这份表格同时也是对评委的诚实交代：我们不是没想到，是拿不到。
